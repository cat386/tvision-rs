# 2. Архитектура

Эта глава объясняет, как устроена программа на tvision-rs: из чего состоит
дерево представлений, как по нему ходят события, как представления
общаются друг с другом и как рисуется экран. Знать это нужно, чтобы писать
свои элементы и не удивляться поведению стандартных.

## Дерево представлений

Всё, что видно на экране, — **представления** (типы с трейтом
[`View`](04-views.md)). Представления-**группы** (`Group` и всё, что
построено вокруг неё: `Window`, `Dialog`, `Desktop`) владеют детьми.
Получается дерево:

```text
Program
└── group (корень, весь экран)
    ├── Desktop                ← рабочий стол (между меню и строкой состояния)
    │   ├── Background         ← узор фона ░░░
    │   ├── Window «Окно 1»
    │   │   ├── ScrollBar
    │   │   └── ListBox
    │   └── Dialog «Настройки» ← модальный диалог тоже живёт на рабочем столе
    │       ├── InputLine
    │       ├── Label
    │       └── Button …
    ├── StatusLine             ← нижняя строка
    └── MenuBar                ← верхняя строка
```

Порядок детей в `Group::children`:

* индекс 0 — **самый нижний** ребёнок, последний — **самый верхний**
  (он рисуется последним и первым получает щелчки мыши);
* порядок перехода по Tab совпадает с порядком вставки;
* у группы есть **текущий** ребёнок (`Group::current`) — тот, что выбран и
  получает клавиатуру. В окне это элемент с фокусом, на рабочем столе —
  активное окно.

Представление в фокусе — это цепочка текущих детей от корня вниз:
корень → рабочий стол → активное окно → его текущий элемент. У всех
представлений этой цепочки установлен флаг `sf::FOCUSED`, у текущего
ребёнка каждой группы — `sf::SELECTED`.

### Идентификаторы вместо указателей

В C++ представления хранили указатели друг на друга (`owner`, `link` у
метки, `vScrollBar` у списка). В Rust такие циклические ссылки неудобны,
поэтому у каждого представления есть уникальный **идентификатор**
`ViewId` (поле `vs.id`), и связи хранятся как id:

```rust
use tvision::*;

fn build() -> Dialog {
    let mut d = Dialog::new(Rect::new(0, 0, 40, 10), "Пример");
    let sb = d.add(ScrollBar::new(Rect::new(30, 2, 31, 7))); // id полосы
    let list = d.add(ListBox::new(Rect::new(2, 2, 30, 7), 1, Some(sb)));
    d.add(Label::new(Rect::new(2, 1, 12, 2), "~С~писок", Some(list)));
    d
}
```

Найти представление по id можно в любой группе или во всей программе:

```rust
use tvision::*;

fn read_list(app: &Program, list: ViewId) -> Option<String> {
    app.find::<ListBox>(list).and_then(|l| l.selected_text().map(String::from))
}
```

`find::<T>` ищет во всём поддереве и приводит к конкретному типу;
`view` / `view_mut` дают `&dyn View` без приведения.

### Представление не знает своего владельца

Это главное отличие от оригинала. В C++ кнопка внутри обработчика могла
вызвать `owner->selectNext()`, метка — `link->select()`, окно —
`owner->remove(this)`. Здесь у представления нет ссылки на владельца.
Вместо этого в `handle_event` передаётся **контекст** [`Ctx`](#контекст-ctx),
и представление оставляет в нём просьбы:

| В C++ | Здесь |
|-------|-------|
| `select()` / `link->select()` | `ctx.select(id)` |
| `owner->selectNext(False)` | `ctx.select_next(true)` |
| `message(owner, evBroadcast, cm, p)` | `ctx.message(cm, info)` |
| `close()` / `destroy(this)` | `ctx.close(id)` |
| `makeFirst()` | `ctx.make_first(id)` |
| `putEvent(e)` | `ctx.put_event(e)` / `ctx.post_command(cm, info)` |
| `owner->execView(d)`, `messageBox` из `handleEvent` | `ctx.exec(Box::new(d), Some(self.vs.id), tag)` |
| `endModal(cmd)` | `ctx.end_modal(cmd)` |
| обращение к `TProgram::application` / `deskTop` | `ctx.with_program(|app| …)` |

Владелец выполняет просьбы **сразу после** возврата из `handle_event`
ребёнка — то есть для ребёнка это выглядит почти как прямой вызов, только
отложенный на мгновение.

## Цикл событий

`Program::run` повторяет один шаг (`Program::step`), пока не придёт
`cm::QUIT`:

```text
┌──────────────────────────────────────────────────────────────────────┐
│ 1. redraw()     нарисовать всё дерево в теневой буфер, вывести        │
│                 в терминал только изменившиеся ячейки                 │
│ 2. get_event()  взять событие из очереди Ctx (put_event), иначе       │
│                 подождать терминал (до 100 мс)                        │
│ 3. handle(ev)   доставить событие (см. ниже)                          │
│ 4. после события: выполнить запросы Ctx (exec, focus, with_program…), │
│                 обновить доступность команд, разослать                │
│                 cm::COMMAND_SET_CHANGED, если команды изменились      │
└──────────────────────────────────────────────────────────────────────┘
```

Если событий нет, вызывается `AppHandler::idle` — аналог `idle()` из
оригинала.

### Доставка события

1. **Открыто меню** — событие получает только сеанс меню.
2. **Идёт модальный диалог** (`exec_view`) — сначала строка состояния
   (чтобы работали её клавиши), затем модальное представление. Щелчки
   мимо модального окна игнорируются. Если событие осталось
   необработанным, его получает `Program::modal_hook` (если задан).
   Обработчик приложения `AppHandler` во время модального цикла **не
   вызывается**.
3. **Обычный режим** — Alt+1…9 выбирает окно по номеру; затем событие
   получает корневая группа и раздаёт его вниз; `cm::QUIT` проверяется
   (`valid`) и завершает цикл; всё необработанное получает
   `AppHandler::handle_event`.

Внутри каждой группы (`Group::handle_group_event`) события раздаются так
же, как в `TGroup::handleEvent`:

| Вид события | Кто получает |
|-------------|--------------|
| **Фокусные**: клавиши (`KeyDown`), команды (`Command`) | 1) дети с `of::PRE_PROCESS` (фаза `Phase::PreProcess`); 2) текущий ребёнок (`Phase::Focused`); 3) дети с `of::POST_PROCESS` (`Phase::PostProcess`) — пока кто-то не обработает |
| **Позиционные**: мышь | самый верхний видимый ребёнок под курсором; если кто-то захватил мышь (`ctx.grab_mouse`) — он |
| **Широковещательные** (`Broadcast`) | все дети по порядку, пока кто-то не обработает |

Фаза доступна обработчику в `ctx.phase`. Например, кнопка реагирует на
свою горячую букву без Alt только в фазе `PostProcess` — то есть если
текущий элемент (скажем, строка ввода) эту букву не взял себе.

**Обработать событие** — значит вызвать `ev.clear()` (превратить его в
`Event::Nothing`). Необработанное событие идёт дальше: к следующему
получателю, к владельцу и в конце концов к обработчику приложения.

Подробнее о видах событий и командах — в [главе 3](03-events.md).

## Контекст `Ctx`

`Ctx` — единственный «канал» представления наружу. Он передаётся в
`handle_event`, `valid`, `exec_result` и `update_commands`. Его основные
возможности:

| Метод | Что делает |
|-------|-----------|
| `put_event(ev)`, `post_command(cm, info)` | поставить событие в очередь (будет обработано на следующем шаге) |
| `message(cm, info)` | разослать широковещательное сообщение всем детям **владельца** (соседям и себе) — сразу после возврата из обработчика |
| `select(id)`, `select_next(fwd)`, `make_first(id)`, `close(id)` | просьбы к владельцу |
| `focus(id)` | передать фокус представлению где угодно в дереве (окно станет активным, элемент — текущим) |
| `end_modal(cmd)` | завершить модальный цикл с кодом |
| `grab_mouse(id)`, `release_mouse()`, `mouse_grabbed_by(id)` | захват мыши: все её события идут одному представлению (замена циклов `while (mouseEvent(...))` из C++) |
| `exec(view, reply_to, tag)`, `exec_near`, `exec_placed` | запустить модальное окно; результат придёт в `View::exec_result` представления `reply_to` |
| `with_program(f)` | выполнить действие с программой после события |
| `popup_menu(menu, pos)` | показать контекстное меню |
| `enable_command`, `disable_command`, `set_command`, `command_enabled` | доступность команд |
| `owner_size()` | размер владельца текущего представления |
| `phase`, `screen_size`, `clipboard` | фаза доставки, размер экрана, буфер обмена |

### Почему сообщения «чуть отложены»

Пусть метка `Label` по Alt+букве хочет выбрать связанную строку ввода.
Метка вызывает `ctx.select(link)` и возвращается. Группа (диалог), из
которой её вызвали, видит в «почтовом ящике» просьбу от своего ребёнка и
выполняет `select_id(link)` — тут же, до доставки события следующему
ребёнку. Глубина отправителя запоминается, поэтому просьба попадает именно
к **его** владельцу, а не к группе выше.

`ctx.message` работает так же: широковещательное сообщение рассылается
детям владельца сразу после возврата. Так полоса прокрутки сообщает
соседнему списку новое положение (`cm::SCROLL_BAR_CHANGED`), а список
полосе — новые пределы (`cm::SCROLL_BAR_SET`).

### Модальные окна изнутри представления

Модальный цикл может запустить только программа, поэтому представление
просит: `ctx.exec(Box::new(dialog), Some(self.vs.id), TAG)`. После текущего
события программа выполняет диалог, а результат приходит обратно:

```rust
use tvision::*;

const TAG_ASK: u16 = 1;

struct AskButton {
    vs: ViewState,
    answer: Option<String>,
}

impl View for AskButton {
    tvision::impl_view_basics!();

    fn draw(&self, dc: &mut DrawCtx) {
        let c = dc.color(1);
        let w = self.vs.size.x.max(0) as usize;
        let mut b = DrawBuffer::new(w);
        b.move_char(0, ' ', c, w);
        b.move_str(0, self.answer.as_deref().unwrap_or("[спросить]"), c);
        dc.write_line(0, 0, self.vs.size.x, 1, &b);
    }

    fn handle_event(&mut self, ev: &mut Event, ctx: &mut Ctx) {
        if let Event::MouseDown(_) = ev {
            let mut d = Dialog::centered(40, 8, "Вопрос");
            d.add(InputLine::new(Rect::new(3, 2, 37, 3), 30));
            d.add(Button::new(Rect::new(14, 4, 26, 6), "O~K~", cm::OK, bf::DEFAULT));
            ctx.exec(Box::new(d), Some(self.vs.id), TAG_ASK);
            ev.clear();
        }
    }

    fn exec_result(&mut self, tag: u16, command: u16, view: Box<dyn View>, _ctx: &mut Ctx) {
        if tag == TAG_ASK && command == cm::OK {
            // Данные диалога: список значений его элементов.
            if let Value::List(v) = view.get_data() {
                self.answer = v.first().and_then(|x| x.as_str()).map(String::from);
            }
        }
    }
}
```

Так в библиотеке работают сообщения валидаторов, окно истории, вопрос
«Сохранить изменения?» редактора и диалоги поиска. Если окно нужно
расположить рядом с другим представлением (как окно истории под строкой
ввода), используйте `ctx.exec_placed` с функцией размещения.

## Отрисовка

Отрисовка в tvision-rs устроена проще, чем в оригинале:

* на **каждом шаге** цикла программа рисует всё дерево заново в теневой
  буфер `ScreenBuffer` (снизу вверх: детей группы, затем их тени);
* терминал (`Backend::flush`) получает буфер и выводит **только
  изменившиеся ячейки**.

Поэтому вызывать `drawView()` после изменения данных не нужно: изменили
поле — на следующем шаге оно нарисуется. Метод `draw(&self, dc)` должен
закрасить **всю** свою область: всё, что не нарисовано, останется от
нижних представлений.

Каждое представление рисует через `DrawCtx` — «окно» в экранный буфер:

* координаты — **локальные** (0,0 — левый верхний угол представления);
* вывод обрезается по видимой области самого представления и всех
  владельцев;
* цвета задаются **номерами** в палитре представления; `DrawCtx` переводит
  номер через цепочку палитр (представление → окно → приложение) в
  реальный атрибут — см. [главу 11](11-colors.md).

Широкие символы (иероглифы, часть эмодзи) занимают две ячейки; `DrawCtx` и
`DrawBuffer` учитывают это автоматически.

## Геометрия

`Point { x, y }` и `Rect { a, b }` — копии `TPoint` и `TRect`:

```rust
use tvision::*;

fn geometry() {
    let r = Rect::new(2, 1, 12, 4); // a=(2,1) включительно, b=(12,4) — нет
    assert_eq!(r.width(), 10);
    assert_eq!(r.height(), 3);
    assert!(r.contains(Point::new(11, 3)));
    assert!(!r.contains(Point::new(12, 3)));
    let inner = r.grown(-1, -1); // (3,2)-(11,3): сжать на 1 с каждой стороны
    let moved = r.moved(5, 0); // (7,1)-(17,4)
    assert!(!inner.intersect(&moved).is_empty());
    let _ = Rect::from_origin_size(Point::new(0, 0), Point::new(80, 25));
}
```

У представления положение хранится в `ViewState`: `origin` — левый
верхний угол **в координатах владельца**, `size` — размер. Удобные
методы: `bounds()` (в координатах владельца), `extent()` (локальные,
от (0,0)), `set_bounds(r)`, `make_local(p)` — перевод точки из координат
владельца в локальные.

> **Важно про мышь.** Событие мыши приходит в представление с
> координатами **владельца** (той же системы, что `vs.origin`). Чтобы
> получить точку внутри представления, вызовите `self.vs.make_local(m.pos)`.

## Изменение размеров

Когда владелец меняет размер (окно растягивают мышью, терминал меняет
размер), группа пересчитывает детей по их `vs.grow_mode` (флаги
`gf::*`, как в оригинале):

| Флаг | Смысл |
|------|-------|
| `gf::GROW_LO_X` | левая граница следует за правым краем владельца |
| `gf::GROW_LO_Y` | верхняя граница следует за нижним краем |
| `gf::GROW_HI_X` | правая граница следует за правым краем |
| `gf::GROW_HI_Y` | нижняя граница следует за нижним краем |
| `gf::GROW_ALL` | все четыре: представление сдвигается вместе с правым нижним углом |
| `gf::GROW_REL` | пропорционально (окна на рабочем столе при изменении размера терминала) |
| `gf::FIXED` | не ограничивать размер размером владельца |

Типичные сочетания:

* растягиваться вместе с окном: `GROW_HI_X | GROW_HI_Y`;
* вертикальная полоса прокрутки у правого края: `GROW_LO_X | GROW_HI_X | GROW_HI_Y`;
* кнопка в правом нижнем углу: `GROW_ALL`.

Свои ограничения размера задаёт метод `View::size_limits` (минимум и
максимум); окна по умолчанию не меньше `MIN_WIN_SIZE` (16×6).
